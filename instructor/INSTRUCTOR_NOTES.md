# Instructor notes

Keep this folder out of the copy you give students (see "Keeping the answers private" below).

Do a full dry run of Parts 3 and 4 on a lab machine before the session. The gym-hil authors report the policy learning the task in about 10 minutes with a human in the loop, but check it on your hardware and with the pinned LeRobot version.

## Preparation checklist

- [ ] One Linux machine per group, X11 session, NVIDIA GPU (learner, actor and MuJoCo all run on it).
- [ ] On every machine: `bash install.sh`, then `python prefetch.py`, then `python check_setup.py` with no FAIL.
- [ ] One gamepad per group (Logitech F310 or Xbox-type). `check_setup.py` prints the detected model. If a model's buttons are mapped wrongly, add it to gym-hil's `controller_config.json` (see the [gym-hil README](https://github.com/huggingface/gym-hil#controller-configuration)).
- [ ] Test the keyboard variant (experiment E) end to end: task `PandaPickCubeKeyboard-v0` with `control_mode: "keyboard"`. The docs only show `"gamepad"`; check the value your LeRobot version expects.
- [ ] W&B: create a team project `tp_hilserl`, or tell students to set `WANDB_MODE=offline` and rely on the manual observer logs.
- [ ] Check the W&B metric names in one run: `python scripts/plot_results.py --runs noHIL --list-metrics`. The script finds them by keyword (`reward`, `intervention`); if the defaults don't match, change the `--reward-key` / `--intervention-key` defaults in `scripts/plot_results.py` so students don't have to.
- [ ] Record 2 episodes with `scripts/record.py` and check the summary it prints (it relies on `LeRobotDataset`; it falls back to pointing at the raw files if the API differs).
- [ ] Run one full `train.py` → learner → actor → `log_progress.py` → `plot_results.py` cycle end to end.
- [ ] Assign one Part 5 experiment (A–F) per group.

## Known pitfalls

- Wayland session: keyboard input is silently ignored. Log in with X11.
- Scripts run over SSH, on Colab or on a JupyterHub: no `DISPLAY`, MuJoCo fails with `GLFWError ... DISPLAY environment variable is missing` / `an OpenGL platform library has not been loaded`. Everything must run on the machine the student sits at.
- A new terminal without `export TP_GROUP=...`: the scripts stop with a clear message. Remind students to set it in each of their 3 terminals.
- `use_torch_compile: true` makes the learner slow to start the first time. Set it to `false` in `configs/train_config.json` if startup takes more than a couple of minutes.
- Two runs on one machine clash on gRPC port 50051. `train.py` and `check_setup.py` warn if the port is busy; `pkill -f lerobot.rl` clears leftovers.
- If W&B is unavailable, students run `plot_results.py --offline`: the plots then come only from the observer logs, so insist that observers log every 5 minutes.
- Students forget to hand control back on the keyboard (Space is a toggle). Remind them before Part 4.

**If time runs short**, drop Part 2 (and experiment C, which uses the Part 2 demos) and shorten Part 5 to 15-minute runs.

## Answer key (main points)

| Q | Expected key points |
| --- | --- |
| 1.1 | Two 128×128 RGB cameras (front, wrist); 18-D state, most likely (from the normalisation ranges): 7 joint positions, 7 joint velocities (the ±100 ranges), gripper opening (0–255), end-effector x, y, z. Action: continuous (dx, dy, dz) in [-1, 1] plus a discrete gripper command (3 values). |
| 1.2 | End-effector deltas cut the action space to 3-D and make actions directly meaningful for the task; the robot solves inverse kinematics each step (plus workspace bounds). Joint-space RL must also learn the arm's kinematics. |
| 1.3 | Sparse reward: 1 on success (cube lifted), 0 otherwise, minus a small gripper penalty (-0.02). Random exploration almost never finds the reward, hence demos and interventions. |
| 2.1 | Off-policy methods learn from transitions generated by any behaviour policy (replay buffer). On-policy gradient estimates need samples from the current policy, so demos would bias them. |
| 2.2 | Useful: successful, consistent, cover varied cube positions, efficient. Harmful: hesitations and back-and-forth, inconsistent strategies for the same state, failed episodes labelled as success. |
| 2.3 | BC on 10 demos overfits; at test time small errors take the policy to states absent from the demos (covariate shift) and errors compound. |
| 3.1 | α trades reward against policy entropy. Too high: near-random behaviour that washes out the effect of interventions and slows learning. Too low: premature convergence, poor exploration. |
| 3.2 | Number of gradient updates per environment step. Values above 1 squeeze more learning from each (expensive) real interaction, at the cost of compute and overfitting risk (hence 2 critics, target networks). |
| 3.3 | The actor collects data with an older policy: less relevant exploration and corrections that target already-fixed mistakes. SAC is off-policy, so stale data is still valid for learning; only efficiency suffers. |
| 3.4 | Frozen: fast, stable, few parameters to learn, less overfitting. Drawback: features not adapted to the task (fine cube/gripper details), limits final precision. |
| 3.5 | 0.97^100 ≈ 0.048. Rewards far in the future are heavily discounted, so the value signal from a sparse end-of-task reward is weak early in the episode; anything that shortens the path to success (demos, interventions) helps a lot. |
| 4.1–4.3 | Data-dependent. Expect HIL to reach first success earlier and the intervention rate to fall over time. A combined metric: success rate per minute of human effort, or time-to-threshold with human time counted at a weight. |
| 4.4 | The actor stores `is_intervention` in the transition's complementary info; the learner adds intervention transitions to the offline (demo) buffer as well as the online buffer, so they are replayed like demonstrations. Check the exact field names in your version. |
| 4.5 | The human labels states the learner itself reached, targeting its own mistakes (the DAgger idea), instead of adding demos from the expert's state distribution. |
| 5.1–5.2 | Hypothesis stated before running; one run per condition is anecdotal: need several seeds and operators, and a pre-registered metric. |
| 6.1 | Class-level: median time to threshold per condition and the spread; explain spread by operator skill, intervention strategy, random seed, machine speed. |
| 6.2 | HG-DAgger: supervised learning on human labels, assumes a near-optimal teacher, cannot exceed it. HIL-SERL: RL with a reward; human actions guide exploration and enter the replay buffer; the policy can outperform the teacher (faster cycle times). |
| 6.3 | A learned reward classifier (or manual labels). Failure modes: false positives exploited by the policy (reward hacking), sensitivity to lighting and background, labelling cost. |
| 6.4 | Intervening too early/too often (policy never explores), long takeovers (data far from the policy's distribution), inconsistent strategies between operators, late interventions after an irreversible failure, forgetting to hand back control. |
| 6.5 | Robot-gated interventions (ask for help when uncertain: ensemble disagreement, low Q-value), shorter corrective primitives (e.g. one "grasp now" button), better interfaces (leader arm, VR), sharing interventions across robots. |

## Keeping the answers private

The simplest option is two repositories:

1. **Public student repo:** everything except `instructor/`.
2. **Private instructor repo:** the full repo.

From the full repo:

```bash
git rm -r --cached instructor && echo "instructor/" >> .gitignore
git commit -m "Remove instructor material from the student repo"
```

Do this before pushing to the public remote, and keep the original with `instructor/` in your private remote.
